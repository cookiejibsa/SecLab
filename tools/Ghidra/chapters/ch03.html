CodeBrowser — 전체 레이아웃

CodeBrowser를 처음 열면 패널이 너무 많아서 어디서 시작해야 할지 막막하다. 핵심은 세 개다. Listing(진실), Decompiler(힌트), Symbol Tree(지도). 이 셋의 관계를 이해하면 나머지는 자연히 따라온다.

Listing 패널 완전 해부

Listing은 디스어셈블리 뷰다. 어셈블리 코드만 보이는 것 같지만, 실제로는 여러 열(column)로 구성된 구조화된 데이터다. 

; Listing 한 줄의 구성 요소:
; [주소]  [원시 바이트]  [명령어]        [오퍼랜드]         [자동 주석]

00401234  55              PUSH       EBP
00401235  89 E5          MOV        EBP,ESP
00401237  83 EC 10       SUB        ESP,0x10
0040123A  E8 C1 FF FF FF CALL       FUN_00401200      ; XRef 있는 호출
0040123F  85 C0          TEST       EAX,EAX
00401241  74 0A          JZ         LAB_0040124D      ; 분기 대상 레이블

원시 바이트 열을 클릭하면 Bytes 뷰와 동기화된다. 주소를 클릭하면 해당 위치로 고정할 수 있다. 열의 너비는 드래그로 조절 가능하고, 우측 상단의 "Edit Listing Fields" 버튼으로 원하는 열만 표시할 수 있다.

Listing ↔ Decompiler 동기화

Listing에서 커서를 어셈블리 줄에 놓으면, Decompiler 창에서 해당 어셈블리에 대응하는 C 코드가 하이라이트된다. 반대도 마찬가지다. 이 동기화가 Ghidra 분석의 핵심 워크플로우다. 

; Listing에서 이 줄에 커서를 놓으면:
0040123A  CALL  FUN_00401200

/* Decompiler에서 이 부분이 하이라이트됨: */
int result = FUN_00401200(param_1);
if (result == 0) {
    ...
}
💡
Decompiler 창에서 직접 변수 이름 변경

Decompiler 창에서 변수 이름에 커서를 놓고 L을 누르면 이름 변경이 된다. 이 변경이 Listing에도 자동으로 반영된다. Decompiler에서 더 빠르게 작업할 수 있다.

XRef (교차 참조) — 분석의 핵심 도구

리버스 엔지니어링에서 가장 자주 하는 질문은 "이 함수는 어디서 호출돼?" 그리고 "이 데이터는 어디서 사용돼?"다. XRef가 그 답을 준다.

함수 이름 위에 커서를 놓고 Ctrl+클릭 또는 X를 누르면 이 함수를 호출하는 모든 위치가 나온다. 호출이 한 곳이면 그냥 이동하고, 여러 곳이면 목록이 팝업된다. 

; 예: check_license 함수의 XRef
; 다음 4곳에서 호출됨을 알 수 있음:

00401100  CALL  check_license   ; main()에서 호출
00402345  CALL  check_license   ; startup_init()에서 호출
00405678  CALL  check_license   ; periodic_check()에서 호출
00406789  CALL  check_license   ; on_connect()에서 호출

라이선스 체크가 4곳에서 호출된다는 걸 발견하면, 크랙을 위해 어떤 조건을 수정해야 할지 전략을 세울 수 있다.

문자열이나 전역 변수 위에서 X를 누르면 이 데이터를 참조하는 모든 코드 위치가 나온다. "password incorrect" 문자열의 XRef를 따라가면 비밀번호 체크 로직을 즉시 찾을 수 있다. 

; Defined Strings에서 "Enter password:" 더블클릭
; → 해당 주소로 이동
; → X를 눌러 XRef 확인
; → 이 문자열을 사용하는 함수로 이동
; → 비밀번호 처리 로직 발견
XRef 타입의미
CALL함수 호출
DATA데이터 읽기/쓰기 참조
READ데이터 읽기
WRITE데이터 쓰기
UNCONDITIONAL_JUMP무조건 점프
CONDITIONAL_JUMP조건부 점프
COMPUTED_JUMP간접 점프 (함수 포인터 등)

Function Graph — CFG 시각적 분석

Ctrl+Shift+G 또는 Window → Function Graph로 열 수 있다. 현재 함수의 제어 흐름 그래프(Control Flow Graph)를 블록 다이어그램으로 보여준다.

각 블록이 기본 블록(Basic Block)이다 — 분기 없이 순차 실행되는 명령어들의 묶음이다. 초록색 화살표가 조건 참(True) 분기, 빨간색이 조건 거짓(False) 분기, 파란색이 무조건 점프다. 

; 함수의 if-else 구조가 CFG에서 어떻게 보이는가:

                    [entry block]
                    TEST EAX, EAX
                    JZ → [false branch]
                    ↓ (true)
              [true branch]           [false branch]
              MOV EAX, 1              MOV EAX, 0
              JMP [exit]              JMP [exit]
                    ↓
                [exit block]
                RETN
💡
Function Graph에서 실수 포인트

함수가 크면 그래프가 너무 복잡해진다. 이럴 때는 관심 있는 블록만 선택해서 "Group"으로 묶거나, Satellite View(우측 하단 소형 맵)를 활용한다. 전체 구조 파악에는 CFG가 유용하고, 세부 분석은 Listing에서 하는 게 낫다.

주석(Comment) 시스템 완전 이해

Ghidra의 주석은 5가지 타입이 있다. 각각 Listing에서 다른 위치에 표시된다.

주석 타입단축키표시 위치용도
EOL Comment;명령어 오른쪽 끝한 줄 메모. "이 레지스터는 파일 핸들"
Pre CommentShift+;명령어 바로 위블록 설명. 여러 줄 가능
Post CommentCtrl+;명령어 바로 아래결과 설명. "여기서 EAX = 성공 여부"
Plate CommentCtrl+Shift+;함수/레이블 위 박스함수 전체 설명. 가장 눈에 띔
Repeatable CommentAlt+;이 주소를 참조하는 모든 곳함수 목적. 호출 지점 전체에 전파
💡
Repeatable Comment 활용법

check_password 함수에 Repeatable Comment로 "Returns 1 if password matches, 0 otherwise"를 달아두면, 이 함수를 호출하는 모든 위치의 CALL 명령어 옆에 해당 주석이 자동으로 표시된다. 분석 결과가 전파되는 효과.

실전 분석 워크플로우 3가지

스트립된 바이너리에서 가장 빠른 시작점. 의미 있는 문자열을 찾아서 로직으로 역추적한다.

  • 1
    Window → Defined Strings로 문자열 창 열기
    필터에 "password", "error", "success", "flag", "key", "invalid" 입력
  • 2
    의미 있는 문자열 더블클릭 → Listing의 해당 주소로 이동
    X로 XRef 확인 → 이 문자열을 사용하는 함수로 이동
  • 3
    해당 함수에서 Decompiler 확인, 이름 변경, 주석 달기
    호출자(caller)를 XRef로 추적하며 위로 올라가기 
; 예: CTF 크랙미 분석
; "Wrong password!" 문자열 XRef → check_input() 발견
; check_input() 분석 → strcmp() 호출 확인
; strcmp() 인자를 추적 → 하드코딩된 비밀번호 발견
00401234  PUSH  0x405000        ; "secret123" ← 이게 비밀번호
00401239  PUSH  EAX              ; 사용자 입력
0040123A  CALL  strcmp

임포트 테이블에서 의심스러운 API를 찾아 사용 지점을 추적한다. 악성코드 분석에 특히 유효하다.

  • 1
    Symbol Tree에서 Imports 펼치기
    kernel32.dll, wininet.dll, ws2_32.dll 등 의심스러운 DLL 확인
  • 2
    의심 API 선택 (예: CreateRemoteThread, VirtualAllocEx, WriteProcessMemory)
    X로 XRef → 사용 지점으로 이동
  • 3
    해당 함수에서 API 호출 패턴 분석
    예: OpenProcess → VirtualAllocEx → WriteProcessMemory → CreateRemoteThread = DLL 인젝션

main 또는 엔트리포인트에서 시작해 위에서 아래로 추적한다. 코드 구조를 전체적으로 파악하고 싶을 때.

  • 1
    Symbol Tree → Functions → entry 또는 main 클릭
    없으면 G를 누르고 entry 입력
  • 2
    Function Graph(Ctrl+Shift+G)로 전체 흐름 조감
    어떤 경로가 있는지 파악 후 Listing으로 세부 분석
  • 3
    CALL 명령어를 만날 때마다 해당 함수로 들어가서 이름 붙이기
    분석이 끝나면 Alt+←로 돌아와 다음 CALL 분석

함수 시그니처 수정 — Decompiler 품질 높이기

Ghidra가 자동으로 추론한 함수 시그니처가 틀릴 때가 많다. 특히 호출 규약이 비표준이거나 파라미터 수가 틀린 경우. 수동으로 수정하면 Decompiler 결과물이 드라마틱하게 좋아진다. 

/* 수정 전: Ghidra 자동 추론 결과 */
void FUN_00401234(undefined4 param_1)
{
    undefined4 uVar1;
    uVar1 = FUN_00401100(param_1, *(undefined4 *)(param_1 + 4));
    ...
}

/* 수정 후: 함수 시그니처 직접 지정 */
/* Edit → Function Signature 또는 함수명 우클릭 → Edit Function Signature */
int check_user_token(UserRecord *user)
{
    int result;
    result = validate_token(user, user->token_length);
    ...
}

UserRecord 같은 커스텀 타입은 Data Type Manager에서 먼저 정의해야 한다. 이 내용은 다음 챕터에서 다룬다.

Binary Patching — 바이너리 수정

Ghidra로 바이너리를 직접 수정할 수 있다. CTF 크랙미에서 조건 분기를 반전시키거나, 안티디버깅 코드를 NOP으로 채우는 등에 사용한다. 

; 방법 1: Instruction Patch (어셈블리 수준 수정)
; Listing에서 수정할 명령어 우클릭 → "Patch Instruction"
; 예: JNZ → JMP (점프 조건 제거)

; 방법 2: Byte Patch (바이트 수준 수정)
; Bytes 뷰에서 직접 수정: 우클릭 → "Byte Viewer Options" 후 편집

; 수정 후 내보내기:
; File → Export Program → Format: Binary (원본 포맷 유지)
⚠️
Patch는 Ghidra 내부 DB에만 반영된다

"Patch Instruction"을 해도 원본 파일은 그대로다. 실제로 수정된 바이너리를 얻으려면 반드시 File → Export Program으로 내보내야 한다.
