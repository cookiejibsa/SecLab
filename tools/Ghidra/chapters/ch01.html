왜 Ghidra인가 — 탄생 배경

2019년 RSA 컨퍼런스에서 NSA(미국 국가안보국)가 발표를 하나 했다. 내부에서만 쓰던 리버스 엔지니어링 도구를 오픈소스로 공개한다는 것이었다. 그게 Ghidra다. 청중 반응은 두 가지였다 — "이게 무료라고?" 그리고 "NSA가 백도어 심어놨겠지?"

두 번째 우려는 실제로 초기에 JDWP 디버그 포트가 특정 조건에서 열린다는 버그가 발견되면서 잠깐 논란이 됐다. 하지만 오픈소스로 소스가 전부 공개됐기 때문에 커뮤니티가 빠르게 검증했고, 악의적 백도어는 없다는 결론이 났다. 소스코드는 지금도 GitHub에서 전부 읽을 수 있다.

NSA가 이걸 만든 이유는 단순했다. IDA Pro는 비쌌고 (라이선스당 수천 달러), 분석가 수십 명이 쓰기엔 예산이 부족했다. 그래서 내부 도구를 수십 년에 걸쳐 개발해왔고, 그게 어느 순간 IDA Pro와 견줄 수 있는 수준이 됐다. 공개한 이유는 "사이버 보안 생태계 강화"가 명분이지만, 사실 오픈소스 커뮤니티의 기여를 통해 도구를 더 발전시키려는 목적도 컸다.

학생, 개인 연구자, CTF 플레이어라면 Ghidra로 시작하는 게 맞다. 무료고, 디컴파일러가 기본 포함이고, 기능도 충분하다. 실무에서 윈도우 악성코드 분석이 주라면 IDA Pro가 여전히 업계 표준이다. 둘 다 배워두는 게 이상적이다.

Ghidra 내부 처리 파이프라인 — 기계어에서 의사코드까지

Ghidra가 바이너리를 분석할 때 내부에서 무슨 일이 일어나는지 알면 결과물을 훨씬 잘 해석할 수 있다. 크게 5단계로 나뉜다.

① 로딩 (Loading)

바이너리 포맷을 파악하고 메모리에 적재한다. PE(Windows), ELF(Linux), Mach-O(macOS), 펌웨어 블랍(raw binary) 등을 처리한다. 이 단계에서 섹션 정보, 임포트/익스포트 테이블, 엔트리포인트가 파악된다. 인식하지 못하는 포맷이면 "Raw Binary"로 로드해서 수동으로 섹션을 정의해야 한다.

② 디스어셈블 (Disassembly)

기계어(바이트)를 어셈블리 명령어로 변환한다. 이때 SLEIGH라는 언어로 작성된 프로세서 명세 파일을 사용한다. SLEIGH는 Ghidra가 50개 이상의 아키텍처를 지원할 수 있는 비결이다. x86-64라면 x86-64.sla를 읽어서 각 바이트 패턴이 어떤 명령어인지 판단한다.

③ PCode 리프팅 (PCode Lifting)

디스어셈블된 어셈블리를 PCode라는 중간 표현 언어(Intermediate Representation)로 변환한다. 이것이 Ghidra의 핵심 차별점이다. 예를 들어 x86의 ADD eax, 4와 ARM의 ADD r0, r0, #4는 PCode 레벨에서 동일하게 표현된다. 덕분에 아키텍처에 상관없이 동일한 분석 알고리즘을 적용할 수 있다. 

; x86 어셈블리
ADD EAX, 4

; PCode로 변환된 결과 (개념적 표현)
tmp = INT_ADD EAX, 4:4
EAX = COPY tmp
CF  = INT_CARRY EAX, 4:4
OF  = INT_SCARRY EAX, 4:4
SF  = INT_SLESS tmp, 0:4
ZF  = INT_EQUAL tmp, 0:4

하나의 어셈블리 명령어가 여러 PCode 연산으로 분해되는 것을 볼 수 있다. 플래그 레지스터 업데이트까지 명시적으로 표현된다. 이 세밀함 덕분에 데이터 흐름 분석(Data Flow Analysis)이 가능해진다.

④ 디컴파일 (Decompilation)

PCode를 분석해서 C와 비슷한 의사코드(pseudo-code)를 생성한다. 이 과정에서 SSA(Static Single Assignment) 형식 변환, 데이터 흐름 분석, 제어 흐름 구조화, 변수 타입 추론이 일어난다. 컴파일러 이론의 역방향이라고 보면 된다. 완벽하지 않기 때문에 결과물을 항상 비판적으로 봐야 한다.

⑤ 분석기 (Analyzers)

Auto Analysis 단계에서 여러 분석기가 병렬로 돌아간다. 주요 분석기들: 함수 경계 감지, 임포트 심볼 해석, 데이터 참조 추적, 문자열 식별, 스택 분석, 호출 규약 적용 등. 분석기는 추가로 개발해서 붙일 수 있다.

Ghidra가 잘하는 것 vs 못하는 것

  • 무료 디컴파일: IDA Pro의 Hex-Rays 없이도 C 수준 의사코드를 볼 수 있다. 이것만으로도 혁명적이다.
  • 다중 아키텍처: x86, x64, ARM, MIPS, PowerPC, RISC-V, AVR, 68k 등 50개 이상. 임베디드/IoT 펌웨어 분석에 강하다.
  • 팀 협업: Shared Project 기능으로 여러 분석가가 같은 바이너리를 동시에 작업할 수 있다.
  • 스크립팅 자동화: Java API가 매우 잘 문서화됐다. Jython(Python)으로도 거의 모든 기능에 접근 가능.
  • 버전 추적: Version Tracking으로 업데이트된 바이너리에서 변경점을 비교할 수 있다. 패치 분석에 유용.
  • 커스터마이징: 오픈소스라서 소스를 수정하거나 Processor Module, Loader를 직접 작성할 수 있다.
  • UI 반응성: Java Swing 기반이라 대형 바이너리(수십 MB)에서 느려질 수 있다. IDA Pro의 Qt UI가 더 빠르다.
  • C++ 역분석: RTTI, vtable, 가상 함수 처리가 IDA Hex-Rays에 비해 떨어진다. 복잡한 C++ 코드는 결과물이 지저분하다.
  • Jython 한계: Python 2.7 기반이라 Python 3 라이브러리를 쓸 수 없다. Ghidra 11.x에서 Python 3 지원이 개선됐지만 아직 완벽하지 않다.
  • 플러그인 생태계: IDA에 비해 서드파티 플러그인이 적다. 특히 특정 바이너리 포맷 지원.
  • 디버거 통합: 내장 디버거는 gdb/WinDbg를 연결하는 방식이라 IDA의 통합 디버거보다 불편하다.

Ghidra의 핵심 개념 — SLEIGH 언어

SLEIGH(Specification Language for Encoding Instructions of Ghidra)는 Ghidra가 새로운 프로세서를 지원하는 방법이다. 직접 만질 일은 많지 않지만, 분석 결과가 왜 그렇게 나오는지 이해하려면 알아야 한다. 

# x86-64의 MOV 명령어 SLEIGH 정의 (단순화 버전)
# SLEIGH 파일은 Ghidra 설치 디렉토리의 Processors/ 하위에 있다

:MOV rm8, r8   is ...
{
    rm8 = r8;    # PCode: COPY 연산으로 변환
}

:MOV rm64, imm64  is ...
{
    rm64 = imm64;
}

SLEIGH 파일은 Ghidra 설치 경로의 Ghidra/Processors/ 폴더 안에 있다. x86-64라면 Processors/x86/data/languages/x86-64.slaspec이다. 왜 디컴파일 결과가 이상하게 나오는지 궁금할 때 여기를 보면 힌트를 얻을 수 있다.

⚠️
디컴파일 결과를 맹신하지 말 것

Ghidra의 디컴파일러는 어디까지나 추정이다. 컴파일러 최적화, 난독화, 핸드어셈블 코드 등에서 틀린 결과를 낸다. 특히 간접 점프(indirect jump), 함수 포인터, 동적 코드 생성에서 자주 오분석한다. 의사코드는 참고용이고, 어셈블리가 진실이다.

Ghidra 10.x / 11.x — 최신 변경사항

2025년 기준 Ghidra 11.x가 최신이다. 주요 변화를 알아두면 오래된 튜토리얼을 볼 때 혼란이 없다.

  • 내장 디버거 (10.0+): gdb, WinDbg, LLDB 연결 없이 Ghidra 안에서 디버깅. GDB와 동일한 인터페이스.
  • Python 3 지원 (10.2+): PyGhidra를 통해 Python 3 환경에서 Ghidra API 호출 가능. Jython 의존도 감소.
  • BSim (Binary Similarity): 함수 해시 기반으로 서로 다른 바이너리에서 유사한 함수를 찾는 기능. 악성코드 패밀리 분류에 유용.
  • 개선된 C++ 지원: RTTI 파싱과 vtable 분석이 꾸준히 개선되고 있다.
