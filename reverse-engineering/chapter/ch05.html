PE / ELF 파일 포맷

실행 파일을 실행하기 전에 파일 자체를 읽는 법을 배운다

왜 파일 포맷을 알아야 하는가

바이너리를 디스어셈블러에 던지기 전, 파일 자체가 말해주는 정보가 있다. 어떤 API를 임포트하는지, 어떤 문자열이 박혀있는지, 얼마나 높은 엔트로피를 가지는지. 이 정보가 이후 분석 전략 전체를 결정한다. 패킹된 파일을 디스어셈블러로 열면 쓰레기 코드만 보인다 — 먼저 파일을 읽어야 알 수 있다.

PE (Portable Executable) 구조

파일 시작
┌─────────────────────────────────┐
│  DOS Header (0x40 bytes)        │  ← MZ 시그니처 (0x4D5A)
│  └ e_lfanew: PE 헤더 오프셋    │
├─────────────────────────────────┤
│  DOS Stub                       │  "This program cannot be run..."
├─────────────────────────────────┤
│  PE Signature ("PE\0\0")        │  ← 0x50450000
├─────────────────────────────────┤
│  COFF Header (File Header)      │  머신 타입, 섹션 수, 타임스탬프
│  Optional Header                │  ImageBase, EntryPoint, 섹션 정렬
│  └ Data Directories             │  임포트/익스포트/리소스 테이블 위치
├─────────────────────────────────┤
│  Section Headers                │  각 섹션의 VA, 크기, 파일 오프셋
├─────────────────────────────────┤
│  .text  (코드)                  │
│  .rdata (읽기 전용 데이터)      │
│  .data  (초기화된 데이터)       │
│  .rsrc  (리소스)                │
│  .reloc (재배치 정보)           │
└─────────────────────────────────┘

임포트 테이블 (IAT) — 분석의 첫 번째 단서

임포트 테이블(Import Address Table)은 이 바이너리가 어떤 DLL의 어떤 함수를 사용하는지 목록이다. 소스코드가 없어도 동작을 추론할 수 있는 가장 강력한 단서다.

임포트 패턴의심되는 행위
CreateRemoteThread, VirtualAllocEx, WriteProcessMemory프로세스 인젝션
RegOpenKeyEx, RegSetValueEx레지스트리 조작 (지속성)
WSAStartup, connect, send, recv네트워크 통신
CryptEncrypt, CryptGenKey, CryptAcquireContext암호화 (랜섬웨어 의심)
GetAsyncKeyState, SetWindowsHookEx키로거
LoadLibrary, GetProcAddress만 있음동적 임포트 — API 숨김 의심
⚠️
동적 임포트 우회

정교한 악성코드는 IAT에 API를 노출하지 않는다. LoadLibraryA와 GetProcAddress만 임포트한 뒤, 런타임에 필요한 API 주소를 직접 계산한다. 이 경우 동적 분석이 필수다.

pestudio로 빠른 분석

; pestudio에서 확인할 것들 (우선순위 순)

1. Indicators 탭
   - 블랙리스트 API 강조 표시
   - 비정상적인 섹션 이름

2. strings 탭
   - URL, IP 주소
   - 레지스트리 키 경로
   - 명령어 문자열 (cmd.exe, powershell 등)
   - Base64처럼 보이는 긴 문자열

3. libraries 탭
   - 임포트된 DLL 목록

4. sections 탭
   - 엔트로피 > 7.0 이면 패킹 또는 암호화 의심
   - 섹션에 실행 권한(x)이 있으면서 쓰기 권한(w)도 있으면 셀프 수정 코드 의심

ELF (Executable and Linkable Format) 구조

┌─────────────────────────────────┐
│  ELF Header (64bytes)           │  ← 매직 \x7fELF, 아키텍처, 진입점
├─────────────────────────────────┤
│  Program Headers (Segments)     │  로더가 메모리에 올릴 때 사용
│  └ LOAD, DYNAMIC, INTERP, ...  │
├─────────────────────────────────┤
│  Sections                       │
│  .text   (코드)                 │
│  .plt    (Procedure Linkage Table)
│  .got    (Global Offset Table)  │
│  .data   (초기화된 데이터)      │
│  .bss    (미초기화 데이터)      │
│  .dynsym (동적 심볼 테이블)     │
│  .dynstr (동적 문자열 테이블)   │
├─────────────────────────────────┤
│  Section Header Table           │  분석 툴이 사용 (없어도 실행됨)

PLT/GOT — 동적 링킹의 메커니즘

Linux의 동적 링킹은 두 단계 간접 참조를 사용한다. 처음 함수를 호출하면 PLT → GOT → linker가 실제 주소를 채워준다. 두 번째 호출부터는 GOT에 직접 주소가 있어 바로 점프한다. 

; printf 첫 번째 호출
call printf@plt      ; PLT 스텁으로 점프

; PLT 스텁 내부
printf@plt:
jmp  [printf@got]    ; GOT 항목으로 점프
push 0x1             ; 심볼 인덱스 (첫 호출 시만)
jmp  plt_resolver    ; linker가 실제 주소를 GOT에 채움
💡
GOT Overwrite — CTF의 단골 기법

쓰기 가능한 GOT를 exploit으로 덮어쓰면 임의 함수 호출을 함수 포인터처럼 리다이렉션할 수 있다. Full RELRO가 활성화된 바이너리는 GOT가 읽기 전용이라 이 기법이 막힌다.

readelf / objdump로 분석

# ELF 헤더 정보
readelf -h target

# 섹션 목록
readelf -S target

# 동적 심볼 (임포트 함수 목록)
readelf -D target

# 보안 기능 확인
checksec --file=target
# 출력 예시:
#   RELRO: Full   STACK CANARY: Yes   NX: Yes   PIE: Yes

# 임포트 함수 목록 (더 간결하게)
objdump -d -j .plt target | grep "^[0-9a-f]"

엔트로피로 패킹 탐지

엔트로피(Entropy)는 데이터의 무작위성을 0~8 범위로 수치화한 값이다. 자연어 텍스트는 ~4.5, 정상 실행 코드는 ~6.0, 암호화·압축 데이터는 7.5~8.0에 분포한다.

엔트로피 범위의미
0 ~ 4.5텍스트, 리소스 — 정상
5.0 ~ 6.5컴파일된 코드 — 정상
6.5 ~ 7.2압축 데이터 — 확인 필요
7.2 ~ 8.0암호화 또는 패킹 — 강력 의심
💡
실습: 첫 3분 분석 루틴

바이너리를 받으면: ① DIE로 패커/컴파일러 확인 → ② pestudio에서 IAT + 문자열 + 엔트로피 확인 → ③ 패킹 의심이면 Ch.12로 이동, 아니면 Ghidra로 정적 분석 시작. 이 3분이 이후 수 시간의 방향을 결정한다.
