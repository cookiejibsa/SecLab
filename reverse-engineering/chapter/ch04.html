Chapter 04 · Part 1 — 기초

메모리 구조 & 스택/힙

프로세스가 메모리를 어떻게 사용하는지 모르면 디버거 화면이 그냥 숫자 덩어리로 보인다

프로세스 메모리 레이아웃

프로그램이 실행되면 OS는 가상 주소 공간(Virtual Address Space)을 할당한다. 64비트 프로세스는 이론상 16EB(엑사바이트)를 사용할 수 있지만, 실제로 사용되는 영역은 몇 가지 구역으로 나뉜다. 

; 전형적인 x64 프로세스 메모리 맵 (낮은 주소 → 높은 주소)

0x0000000000000000  ┌──────────────────────────┐
                    │  NULL / 접근 불가 영역    │  (페이지 폴트 유발)
0x0000000000400000  ├──────────────────────────┤
                    │  .text (코드 섹션)        │  실행 가능, 읽기 전용
                    │  .rodata (읽기 전용 데이터)│  문자열 리터럴 등
                    │  .data (초기화된 전역변수) │  읽기/쓰기
                    │  .bss  (미초기화 전역변수) │  읽기/쓰기, 0으로 초기화됨
                    ├──────────────────────────┤
                    │  힙 (Heap)               │  ↑ 위로 성장
                    │  ...                     │
                    │  (빈 공간)               │
                    │  ...                     │
                    │  스택 (Stack)            │  ↓ 아래로 성장
0x00007fffffffffff  ├──────────────────────────┤
                    │  커널 공간 (접근 불가)    │
0xffffffffffffffff  └──────────────────────────┘

스택 (Stack)

스택은 함수 호출의 무대다. 함수를 호출할 때마다 "스택 프레임(Stack Frame)"이 생성되고, 함수가 반환될 때 제거된다. LIFO(Last-In-First-Out) 구조.

스택 프레임 해부

; 함수 foo(int a, int b)를 호출하는 과정

; [1] 인자 전달 (x64 Linux: RDI, RSI / Windows: RCX, RDX)
mov  edi, 1          ; a = 1
mov  esi, 2          ; b = 2
call foo

; [2] call 명령어 = push RIP + jmp
;     스택에 복귀 주소(Return Address)가 쌓임

; [3] foo 내부 — 프롤로그
foo:
push rbp            ; 호출자의 RBP 저장
mov  rbp, rsp       ; 현재 RSP를 새 RBP로
sub  rsp, 0x10      ; 로컬 변수 16바이트 공간

; 스택 레이아웃 (RBP 기준)
;  rbp+0x10  : a (스택으로 넘어온 인자, 있으면)
;  rbp+0x08  : return address
;  rbp+0x00  : saved rbp  ← RBP가 여기를 가리킴
;  rbp-0x08  : local_var1
;  rbp-0x10  : local_var2  ← RSP
💡
Return Address — 공격의 핵심 타겟

버퍼 오버플로우가 위험한 이유가 여기 있다. 스택에 있는 Return Address를 덮어쓰면 함수가 반환될 때 임의의 주소로 실행 흐름을 바꿀 수 있다. RE 과정에서 이 주소를 조작하는 패턴을 보면 취약점 또는 보호 우회 시도다.

힙 (Heap)

스택이 "자동 관리"라면 힙은 "수동 관리"다. malloc()/new로 요청하고, free()/delete로 반환한다. OS는 힙 메모리를 청크(Chunk) 단위로 관리한다.

glibc 힙 청크 구조 (Linux)

; malloc(0x20)으로 할당된 청크의 메모리 레이아웃

0x555555559000:  0x0000000000000000  ; prev_size (이전 청크가 free일 때만 유효)
0x555555559008:  0x0000000000000031  ; size = 0x30, flags (LSB 3비트)
0x555555559010:  ← malloc()이 반환하는 포인터 (user data 시작)
                   ...  (0x20 바이트의 사용자 데이터)
0x555555559030:  0x0000000000000000  ; 다음 청크의 prev_size
0x555555559038:  0x0000000000020fd1  ; top chunk size
💡
RE에서 힙 분석이 중요한 이유

악성코드는 힙에 페이로드를 동적으로 구성하고 실행하는 경우가 많다. Use-After-Free, Heap Spray 같은 익스플로잇 기법도 힙 구조를 이해해야 분석할 수 있다.

섹션별 특성

섹션권한담긴 것RE에서 주목할 점
.text r-x 실행 코드 함수들이 여기 있다. 쓰기 권한이 있으면 셀프 수정 코드(Self-Modifying Code) 의심
.data rw- 초기화된 전역/정적 변수 암호화 키, 설정값이 여기 박혀있는 경우 많음
.rdata r-- 읽기 전용 데이터 (PE) 문자열, 가상 함수 테이블(vtable), 임포트 테이블
.bss rw- 초기화 안 된 전역 변수 런타임에 값이 쓰인다. 파일 크기에는 포함되지 않음
.idata rw- 임포트 주소 테이블 (PE) 어떤 API를 쓰는지 한눈에 파악. IAT 후킹의 대상

가상 주소 vs 파일 오프셋

디스어셈블러와 헥스 에디터를 동시에 쓸 때 혼동이 오는 부분이다. 디스어셈블러는 가상 주소(VA)로 표시하고, 헥스 에디터는 파일 오프셋으로 표시한다. 

; VA → 파일 오프셋 변환
; 파일 오프셋 = VA - 섹션 VA + 섹션 파일 오프셋

; 예시: .text 섹션
;  섹션 VA           = 0x401000
;  섹션 파일 오프셋  = 0x400
;  분석하려는 VA     = 0x401234
;  파일 오프셋       = 0x401234 - 0x401000 + 0x400 = 0x634

pestudio나 Ghidra에서 섹션 정보를 보면 이 값들을 바로 확인할 수 있다. 패치를 파일에 직접 적용할 때 이 계산이 필요하다.

ASLR과 그 한계

ASLR(Address Space Layout Randomization)은 스택, 힙, 라이브러리의 베이스 주소를 실행마다 랜덤화한다. 하지만 PIE(Position-Independent Executable)가 비활성화된 실행 파일은 .text 섹션이 고정 주소에 로드된다.

ASLR 대상랜덤화 여부확인 방법
스택✅ 항상실행마다 RSP 값 다름
힙✅ 항상malloc 반환 주소가 다름
라이브러리 (.so/.dll)✅ 항상kernel32.dll 베이스 주소가 다름
실행 파일 자체PIE 여부에 따라checksec 또는 DIE로 확인
⚠️
디버거에서 주소가 매번 다른 이유

디버거를 재시작할 때마다 스택과 힙의 주소가 바뀐다. 브레이크포인트는 주소가 아니라 심볼이나 오프셋으로 거는 습관을 들이자. x64dbg에서는 모듈+오프셋 형식으로 설정한다.
