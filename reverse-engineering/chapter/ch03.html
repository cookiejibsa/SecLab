RE에서 어셈블리를 읽는 방식

어셈블리를 처음 배울 때는 "어떻게 프로그램을 짜는가"에 집중한다. RE에서는 방향이 반대다 — "이 기계어가 원래 어떤 C 코드였는가"를 역추적한다. 패턴 인식이 핵심이다. 루프가 어떻게 생겼는지, 조건 분기가 어떻게 생겼는지, 함수 호출이 어떻게 생겼는지를 눈에 익혀두면 디스어셈블리를 C처럼 읽을 수 있다.

패턴으로 읽는 어셈블리

① if-else 패턴

; C 코드: if (x == 0) { ... } else { ... }
cmp  eax, 0         ; eax - 0 → 플래그 세팅
jne  else_branch   ; ZF==0이면 else로 점프
; --- if 블록 ---
...
jmp  end_if
else_branch:
; --- else 블록 ---
...
end_if:

② for 루프 패턴

; C 코드: for (int i = 0; i < 10; i++) { ... }
mov  ecx, 0          ; i = 0
loop_start:
cmp  ecx, 10         ; i < 10 ?
jge  loop_end       ; i >= 10 이면 종료
; --- 루프 바디 ---
...
inc  ecx            ; i++
jmp  loop_start
loop_end:

③ 함수 프롤로그/에필로그

; 프롤로그 — 함수의 시작
push rbp            ; 이전 프레임 포인터 저장
mov  rbp, rsp       ; 새 프레임 포인터 설정
sub  rsp, 0x40      ; 로컬 변수 공간 확보

; ... 함수 바디 ...

; 에필로그 — 함수의 끝
mov  rsp, rbp       ; 스택 복원
pop  rbp            ; 이전 프레임 포인터 복원
ret                  ; 호출자로 복귀
💡
최적화된 바이너리에서는 프롤로그가 없을 수 있다

컴파일러 최적화(-O2 이상)를 적용하면 RBP를 생략하고 RSP 상대 주소로 로컬 변수를 참조하는 framepointer omission을 사용한다. 디컴파일러가 헷갈려하는 주요 원인 중 하나다.

④ switch-case 패턴

; 점프 테이블 방식 (컴파일러가 최적화한 switch)
cmp  eax, 4          ; case 범위 초과 체크
ja   default_case    ; 4 초과면 default
jmp  [rax*8 + jump_table]  ; 점프 테이블 인덱싱

jump_table:
dq   case0, case1, case2, case3, case4

점프 테이블은 Ghidra에서 데이터 섹션에 포인터 배열로 보인다. 이 패턴을 인식하면 switch 구조를 바로 알아볼 수 있다.

자주 보이는 관용 표현

어셈블리 의미 설명
xor eax, eax eax = 0 mov eax, 0보다 1바이트 짧다. 컴파일러가 자주 생성.
test eax, eax if (eax == 0)? eax & eax → ZF 세팅. cmp eax, 0보다 짧다.
lea rax, [rbp-0x10] rax = &local_var 포인터를 계산해서 넣는다. 덧셈 용도로도 자주 남용됨.
push rbx; ... pop rbx callee-saved 레지스터 보존 callee가 RBX를 쓰면 반드시 복원해야 한다.
call __alloca_probe 큰 스택 공간 확보 Windows의 가드 페이지 탐색. 큰 로컬 배열이 있을 때 등장.
rep stosd memset() ECX번 반복해서 EAX 값을 [EDI]에 쓴다. 버퍼 초기화.
rep movsd memcpy() ECX번 반복해서 [ESI] → [EDI] 복사.

플래그와 조건 점프

명령어조건C 표현
je / jzZF=1a == b
jne / jnzZF=0a != b
jl / jngeSF≠OFa < b (signed)
jle / jngZF=1 또는 SF≠OFa <= b (signed)
jg / jnleZF=0 그리고 SF=OFa > b (signed)
jb / jnaeCF=1a < b (unsigned)
ja / jnbeCF=0 그리고 ZF=0a > b (unsigned)
⚠️
signed vs unsigned 주의

jl과 jb는 둘 다 "미만"이지만 signed/unsigned가 다르다. 특히 크기 비교나 배열 인덱스 검사 코드에서 혼동하면 버그의 원인이나 취약점을 잘못 해석할 수 있다.
